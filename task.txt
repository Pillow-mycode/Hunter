【任务 1.1】创建 LLM Provider 抽象基类
  文件：hunter-server/llm/base.py
  依赖：无
  设计：
    - 抽象类 BaseProvider，定义统一接口，所有厂商 Provider 继承它
    - 接口方法：
      * chat(messages, **kwargs) -> str
        — 非流式调用，返回完整回复文本
      * chat_stream(messages, **kwargs) -> Generator[str]
        — 流式调用，yield 文本 chunk。默认实现：调用 chat() 后 yield 整个结果
      * supports_json_mode() -> bool
        — 是否支持原生 response_format={"type": "json_object"}
      * get_context_limit() -> int
        — 返回该模型的最大上下文 token 数
      * health_check() -> bool
        — 发送一条最小消息测试连通性
    - __init__(api_key, base_url, model, **extra_params)
      — 子类在 __init__ 中创建底层客户端（如 openai.OpenAI）
    - 内置 _merge_kwargs(kwargs) 方法：
      — 合并默认参数（temperature, max_tokens 等），子类可覆盖默认值

  验收：
    1. 可以用 BaseProvider 类型注解所有 Provider
    2. 至少有一个测试用例：创建 mock Provider 验证接口可调用

【任务 1.3】创建 Provider 工厂
  文件：hunter-server/llm/factory.py
  依赖：1.1, 1.2

  核心函数：
    ProviderFactory.create(provider_type, api_key, base_url=None, model=None) -> BaseProvider
      — 根据 provider_type 字符串创建对应 Provider 实例
      — provider_type 不在已注册列表 → fallback 到 openai_compat_provider

    ProviderFactory.auto_detect(base_url: str) -> str
      — 根据 base_url 关键词匹配厂商（如 "deepseek.com" → "deepseek"）
      — 匹配不到 → 返回 "openai_compat"

    ProviderFactory.list_presets() -> List[dict]
      — 返回所有已注册 Provider 的预设信息（provider_type, base_url, models）
      — 供前端 /api/config/presets 使用

    ProviderFactory.create_from_env(agent_type: str) -> BaseProvider
      — agent_type ∈ {"leader", "attacker", "hawkeye", "analyst"}
      — 读取环境变量：{AGENT_TYPE}_API_KEY / DEFAULT_API_KEY 等
      — base_url → auto_detect → create
      — 已创建的实例缓存起来（同 agent_type 不重复创建）

  验收：
    1. 调用 ProviderFactory.list_presets() 返回至少 deepseek + openai_compat
    2. 调用 ProviderFactory.create_from_env("leader") 根据当前 .env 创建出正确 Provider

【任务 1.4】兼容性处理（JSON 模式 + 异常映射）
  文件：hunter-server/llm/compat.py
  依赖：1.1

  两个工具函数：

  1. parse_json_response(raw_text: str) -> dict
     — LLM 返回的文本可能被 markdown 代码块包裹（```json ... ```）
     — 也可能在 JSON 前后有废话文字
     — 该函数负责：trim 非 JSON 内容 → json.loads → 返回 dict
     — 解析失败 → 抛出 LLMJsonParseError（自定义异常）

  2. map_provider_error(exception: Exception) -> Exception
     — 将各厂商的原始异常映射为项目标准异常：
       * 429 / rate_limit → RateLimitError（附带 retry_after 秒数）
       * 401 / 403 → AuthError（提示检查 API Key）
       * 400 + "context length" → ContextTooLongError（触发截断）
       * 其他 → LLMAPIError（保留原始错误信息）

  验收：
    1. parse_json_response("```json\n{\"a\":1}\n```") 返回 {"a": 1}
    2. parse_json_response("前面废话{\"a\":1}后面废话") 返回 {"a": 1}

【任务 2.1】新增配置管理 API 端点
  文件：hunter-server/server/config_api.py
        hunter-server/server/app.py（挂载路由）
  依赖：1.3（需要 ProviderFactory.list_presets()）

  新增 5 个 HTTP 端点：

  GET  /api/config
    → 返回当前所有 Agent 的配置（provider_type, base_url, model, api_key 脱敏后）
    → api_key 脱敏规则：8 字符以内显示 ****，超过的显示前4后4中间用 **** 替代

  POST /api/config
    → 接收 JSON body，格式：
      {
        "default": {"provider_type": "deepseek", "base_url": "...", "model": "...", "api_key": "..."},
        "leader": {...},   // 可选，留空则用 default
        "attacker": {...},
        "hawkeye": {...},
        "analyst": {...}
      }
    → 写入 .env 文件 + 调用 ConfigManager.reload() 触发热加载

  GET  /api/config/presets
    → 返回 ProviderFactory.list_presets() 的结果

  POST /api/config/test
    → 接收 {"provider_type": "...", "base_url": "...", "model": "...", "api_key": "..."}
    → 创建临时 Provider 实例调用 health_check()
    → 返回 {"ok": true, "latency_ms": 230} 或 {"ok": false, "error": "..."}

  POST /api/config/reload
    → 调用 ConfigManager.reload()，强制从 .env 重读所有配置

  安全要求：
    - GET /api/config 返回的 api_key 必须脱敏
    - 所有端点不需要认证（内网工具），但记录调用日志

  验收：
    1. curl GET /api/config/presets 返回预设厂商列表
    2. curl POST /api/config/test 能测试 deepseek 连通性
    3. POST /api/config 更新配置后，GET /api/config 返回新值

    5.7       → Agent 适配（4 个 Agent 改造为 AgentLoop 模式）

【任务 5.1】团队通信协议
  文件：hunter-server/agent/team/protocol.py
  依赖：无

  InterAgentMessage 数据结构（Python dataclass）：
    @dataclass
    class InterAgentMessage:
        msg_id: str           # 唯一ID，格式 "msg-{uuid8}"
        from_agent: str       # 发送者: leader / tool_master / data_analyst / hawkeye
        to_agent: str         # 接收者: 同上
        msg_type: str         # 消息类型（见下表）
        content: str          # 自然语言消息体（模拟同事对话）
        task_id: Optional[str] = None      # 关联的任务ID
        context_json: Optional[dict] = None # 附带的结构化上下文
        expect_reply: bool = False          # 是否需要回复
        reply_to: Optional[str] = None      # 回复哪条消息的 msg_id
        timestamp: str = field(default_factory=lambda: datetime.now().isoformat())

  消息类型枚举（msg_type 的合法值）：
    delegation        — 派发任务（Leader→TM, TM→DA, Leader→DA）
    task_result       — 任务完成汇报（TM→Leader, DA→TM, DA→Leader）
    query             — 询问进展/状态
    input_alert       — 交互告警（Hawkeye→TM）
    timeout_alert     — 超时告警（Hawkeye→TM, Hawkeye→Leader）
    process_stalled   — 进程停滞告警（Hawkeye→Leader）
    finding_alert     — 发现告警（任何人→Leader）
    analysis_request  — 请求分析（TM→DA, Leader→DA）
    analysis_result   — 分析结果（DA→TM, DA→Leader）
    help_request      — 请求帮助（TM→Leader）
    ack               — 确认收到（用于 expect_reply=True 的回复）

  验收：
    1. 创建一条 InterAgentMessage，to_dict() / from_dict() 可序列化往返
    2. msg_type 枚举值不可随意扩展，修改需同时更新接收方的处理逻辑

【任务 5.2】通信总线 CommBus（含异步队列 + 同步等待）
  文件：hunter-server/agent/team/comm_bus.py
  依赖：5.1, 5.4

  CommunicationBus 是消息路由中心。**一次建完**，同时支持异步和同步两种模式。

  核心数据结构：
    self.inboxes: Dict[str, queue.Queue] = {
        "leader": Queue(),           # Leader 的接收队列
        "tool_master": Queue(),      # ToolMaster 的接收队列
        "data_analyst": Queue(),     # DataAnalyst 的接收队列
        "hawkeye": Queue(),          # Hawkeye 的接收队列
    }
    self._pending_replies: Dict[str, Tuple[threading.Event, list]] = {}
    # 用于同步等待：{msg_id: (event, [result_holder])}

  核心方法：

    def send(self, msg: InterAgentMessage) -> None:
        """异步发送。投递到 to_agent 的队列，持久化到 agent_messages 表。"""
        if msg.to_agent in self.inboxes:
            self.inboxes[msg.to_agent].put(msg)
            self._persist(msg)

    def drain_inbox(self, agent_id: str) -> List[InterAgentMessage]:
        """批量取走 agent_id 收件箱中的所有消息（非阻塞）。"""
        # 从 self.inboxes[agent_id] 取走所有消息，返回列表

    def send_and_wait(self, msg: InterAgentMessage, timeout: float = 300) -> InterAgentMessage:
        """同步发送并等待回复。用于兼容旧代码和 CLI 模式。
           发送 msg → 阻塞等待 → 收到回复后返回。
           超时抛出 TimeoutError。"""
        # 内部：创建 Event → 注册到 _pending_replies → send(msg) → event.wait(timeout)

    def reply(self, to_msg_id: str, reply_msg: InterAgentMessage) -> None:
        """回复某条消息。触发 send_and_wait 中等待的 Event。"""
        # 从 _pending_replies 找到 to_msg_id 对应的 Event → set() → 投递 reply_msg

    def broadcast(self, msg: InterAgentMessage) -> None:
        """向所有 Agent 广播消息（如紧急中止指令）。"""

  关键实现细节：
    - 使用 queue.Queue（线程安全），不依赖 asyncio
    - _persist() 写入 SQLite agent_messages 表
    - send_and_wait() 内部用 threading.Event 阻塞当前线程
    - get_team_status() 返回各 Agent 的 inbox 大小 + Blackboard 中的状态

  验收：

    2. 多线程：线程A send，线程B drain_inbox 能收到
    3. send_and_wait 在收到 reply 前阻塞，收到后正确返回

【任务 5.6】AgentLoop 引擎
  文件：hunter-server/agent/team/agent_loop.py
  依赖：5.2, 5.3, 5.5

  驱动每个 Agent 的 POLL→PROCESS→THINK→ACT 循环的核心引擎。
  每个 Agent 在自己的线程中运行一个 AgentLoop 实例。

  核心类：
    class AgentLoop(threading.Thread):
        def __init__(self, agent: AgentBase, comm_bus, blackboard):
            super().__init__(daemon=True)
            self.agent = agent
            self.comm_bus = comm_bus
            self.blackboard = blackboard
            self.outstanding_tasks: Dict[str, OutstandingTask] = {}
            self.mission_complete = threading.Event()

        def run(self):
            while not self._should_stop():
                self._phase_poll()      # drain_inbox → 分类消息
                self._phase_process()   # 匹配结果到 outstanding_tasks，更新 blackboard
                self._phase_think()     # 构建决策上下文 → 调 agent.decide(context)
                self._phase_act()       # 执行 decide() 返回的决策
                time.sleep(0.5)         # 防 CPU 空转

  辅助数据类：
    @dataclass
    class OutstandingTask:
        task_id: str
        target_agent: str
        instruction: str
        status: str           # PENDING / COMPLETED / TIMEOUT
        sent_at: datetime
        timeout: float = 300

  THINK 阶段构建的决策上下文（传入 agent.decide()）：
    {
        "mission":           blackboard 中的任务目标,
        "outstanding_tasks": "⏳ task_1: 派发给 tool_master (45s)...\n✅ task_2: 已完成",
        "new_inbox":         "📩 来自 tool_master: 端口扫描完成，发现 22/80/443...",
        "blackboard_summary":"已发现 3个子域名, 2个端口, 0个漏洞",
        "team_status":       "tool_master 正在执行 nmap, data_analyst 空闲",
        "history":           "最近 5 条对话历史"
    }

  ACT 阶段支持的决策类型：
    - {"type": "delegate", "target": "tool_master", "content": "请扫描端口..."}
      → 发送 InterAgentMessage，加入 outstanding_tasks，不等待，进入下一轮
    - {"type": "execute_local", "action": "shell", "command": "nmap ..."}
      → AgentLoop 调用 agent.execute_local(action)
    - {"type": "wait", "reason": "等待更多结果"}
      → 短暂休眠后继续循环
    - {"type": "complete", "summary": "任务完成..."}
      → 设置 mission_complete，退出循环

  验收：
    1. 新建 mock Agent，在 decide() 中返回 delegate → AgentLoop 发送消息并继续循环
    2. 对方 Agent 的 drain_inbox() 收到消息
    3. 对方回复后，原 Agent 的下一次 POLL 收到结果

【任务 5.10】Hawkeye 四层检测体系重构（替换现有指数退避轮询）

  文件：
    新建 hunter-server/agent/system/pty_monitor.py       （PTY 输出事件监听器）
    修改 hunter-server/agent/system/system_command.py    （替换 TimeCountThread）
    修改 hunter-server/agent/smart_brain/hawkeye.py       （Hawkeye 继承 AgentBase）
  依赖：5.2（CommBus），5.7（ToolMaster 适配 AgentLoop）

  问题分析：

  当前 Hawkeye 设计存在三个根本缺陷：
    a) 指数退避轮询（2s→4s→8s→...）是"等间隔检查"，如果交互提示
       在第 3 秒出现、第 3.5 秒被进程自动跳过，Hawkeye 根本看不到。
    b) 只检查"是否在交互"，不关心"命令是否执行超时"。
       `whoami` 执行了 300 秒显然不是交互问题，但鹰眼当成交互处理。
    c) 每个周期都调用 LLM，在高速 check 时浪费 token。

  借鉴 Claude Code 的设计思路（PTY 事件驱动 + 分层检测），重新设计为
  四层检测体系，从快到慢、从便宜到昂贵逐层递进：

  ┌─────────────────────────────────────────────────────────────────┐
  │                    Hawkeye 四层检测体系                           │
  │                                                                 │
  │  Layer 1: 模式匹配（微秒级，零 LLM 调用）                         │
  │  ├─ 预编译正则表，命中直接返回，不走 LLM                          │
  │  ├─ 每次 PTY 有新输出时触发检查                                   │
  │  └─ 处理 ~90% 的交互场景                                          │
  │         ↓ 未命中                                                 │
  │  Layer 2: 输出停滞检测（秒级，零 LLM 调用）                        │
  │  ├─ 输出停止流动 N 秒 + 最后一行"看起来像提示词"                   │
  │  ├─ 启发式规则：行末以 :/?/> 结尾 + 无换行 >2s                    │
  │  └─ 处理 ~8% 的交互场景                                           │
  │         ↓ 未命中                                                 │
  │  Layer 3: LLM 判断（仅模糊场景，~2% 的场景）                       │
  │  ├─ 输出停滞超过阈值，但 L1/L2 都无法确定                         │
  │  ├─ 取最后 500 字符，发给 Hawkeye LLM                            │
  │  └─ 保留现有 Hawkeye 的 LLM 调用逻辑，但触发条件更精确             │
  │         ↓                                                        │
  │  Layer 4: 命令时长异常检测（独立于交互检测的并行通道）              │
  │  ├─ 维护一个"命令→预期时长"映射表                                  │
  │  ├─ 命令执行超过预期上限 → 发 InterAgentMessage 给 Leader/TM       │
  │  └─ 解决"whoami 为什么跑了 5 分钟"的问题                           │
  └─────────────────────────────────────────────────────────────────┘

  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  核心类：PTYOutputMonitor（替换 TimeCountThread）

  class PTYOutputMonitor:
      """
      事件驱动的 PTY 输出监控器。
      不轮询！而是：
        - 有新输出时 → 触发 Layer 1（模式匹配）
        - 输出停止流动时 → 每秒检查一次停滞时间 → 触发 Layer 2/3
        - 命令开始时 → 启动 Layer 4 计时器
      """

      def __init__(self, stall_threshold=2.0, anomaly_check_interval=10):
          self.output_buffer = ""         # 滑动窗口，保留最近 2000 字符
          self.last_output_time = time.time()
          self.command_start_time = None  # 当前命令的开始时间
          self.current_command = ""       # 当前命令文本
          self.stall_threshold = stall_threshold  # 输出停滞多少秒算"卡住了"
          self.comm_bus = None            # 用于发送 InterAgentMessage

          # Layer 1: 预编译交互提示正则表
          self.interaction_patterns = [
              (re.compile(r'\[sudo\]\s+password\s+for\s+\w+\s*:?\s*$', re.I), 'sudo_password'),
              (re.compile(r'Password:\s*$'), 'password'),
              (re.compile(r'Enter\s+password\s*:?\s*$', re.I), 'password'),
              (re.compile(r'\[y/[Nn]\]\s*$'), 'yes_no'),
              (re.compile(r'\[Y/n\]\s*$'), 'yes_no'),
              (re.compile(r'\(yes/no\)\s*$', re.I), 'yes_no'),
              (re.compile(r'Continue\?\s*\[?\s*(y|yes|n|no)\s*\]?\s*$', re.I), 'confirm'),
              (re.compile(r'Are\s+you\s+sure\?\s*$', re.I), 'confirm'),
              (re.compile(r'Press\s+(any\s+key|Enter|return)\s*', re.I), 'press_key'),
              (re.compile(r'请输入.*[:：]?\s*$'), 'input_zh'),
              (re.compile(r'确认.*[:：]?\s*$'), 'confirm_zh'),
              (re.compile(r'\[确认\]\s*$'), 'confirm_zh'),
              # General heuristic: line ending with : or ? with no following output
          ]

      def feed_output(self, new_chars: str):
          """PTY 每次有新输出时调用此方法"""
          self.output_buffer = (self.output_buffer + new_chars)[-2000:]
          self.last_output_time = time.time()

          # Layer 1: 立即检查模式匹配
          tail = self.output_buffer[-500:]
          for pattern, prompt_type in self.interaction_patterns:
              if pattern.search(tail):
                  return DetectionResult(
                      detected=True, method='pattern',
                      prompt_type=prompt_type, confidence=0.98,
                      matched_text=pattern.search(tail).group()
                  )
          return DetectionResult(detected=False)

      def check_idle(self) -> DetectionResult:
          """
          每秒由监控线程调用一次。
          仅在输出停滞时进行判断，不做 LLM 调用。
          """
          idle_sec = time.time() - self.last_output_time

          if idle_sec < self.stall_threshold:
              return DetectionResult(detected=False, method='idle_check')

          # 输出已停滞超过阈值
          tail = self.output_buffer[-500:]

          # Layer 2: 启发式判断"最后一行像不像在等输入"
          last_line = tail.split('\n')[-1].strip()
          if self._looks_like_prompt(last_line):
              return DetectionResult(
                  detected=True, method='heuristic',
                  prompt_type='generic_prompt', confidence=0.75,
                  context=f"最后一行: '{last_line[:100]}', 停滞 {idle_sec:.0f}s"
              )

          # Layer 3 trigger: 停滞时间超过 2 倍阈值 → 建议 LLM 介入
          if idle_sec >= self.stall_threshold * 2:
              return DetectionResult(
                  detected=True, method='llm_needed',
                  prompt_type='unknown', confidence=None,
                  snippet=tail[-300:],
              )

          return DetectionResult(detected=False, method='idle_check')

      def _looks_like_prompt(self, line: str) -> bool:
          """判断一行文本是否'看起来像在等输入'"""
          if not line:
              return False
          # 规则1：以 : 或 ? 结尾且不含句号
          if line[-1] in (':', '?', '>', '》'):
              return True
          # 规则2：以常见中文提示词结尾
          if any(line.endswith(w) for w in ['输入', '确认', '继续', '密码', '口令']):
              return True
          return False

      # ─── Layer 4: 命令时长异常检测 ───

      def start_command(self, command: str):
          """记录命令开始执行"""
          self.command_start_time = time.time()
          self.current_command = command

      def check_duration_anomaly(self) -> Optional[dict]:
          """
          检查当前命令是否执行超时（基于命令→预期时长映射）。
          返回 None = 正常，返回 dict = 异常信息。
          """
          if not self.command_start_time:
              return None
          elapsed = time.time() - self.command_start_time
          expected = self._estimate_duration(self.current_command)

          if expected and elapsed > expected['max_seconds']:
              return {
                  'command': self.current_command,
                  'elapsed_seconds': elapsed,
                  'expected_max': expected['max_seconds'],
                  'level': 'critical' if elapsed > expected['max_seconds'] * 2 else 'warning',
              }
          return None

      def _estimate_duration(self, command: str) -> dict:
          """
          根据命令特征估算预期执行时长。
          返回 {'min_seconds': X, 'max_seconds': Y, 'reason': '...'}
          返回 None 表示无法估算。

          策略：
            1. 匹配已知工具 + 参数模式
            2. 没有匹配 → 基于命令类型估算（简单命令 5s，网络命令 120s）
            3. 实在不知道 → 返回 None（不报警）
          """
          cmd = command.strip()

          # 已知工具估算表
          KNOWN_DURATIONS = [
              # (关键词, 最小秒, 最大秒, 原因)
              (['whoami', 'id', 'pwd', 'ls', 'cat', 'echo', 'date', 'uname',
                'hostname', 'which', 'whereis'], 0, 3, '瞬时命令'),
              (['nmap -sn', 'nmap -sL'], 5, 120, 'nmap 主机发现'),
              (['nmap -sV', 'nmap -sC', 'nmap -A'], 30, 600, 'nmap 服务扫描'),
              (['nmap -p-'], 60, 3600, 'nmap 全端口扫描'),
              (['nmap'], 10, 300, 'nmap 默认扫描'),
              (['gobuster', 'dirb', 'dirsearch', 'feroxbuster', 'ffuf'], 30, 1800, '目录扫描'),
              (['sqlmap'], 60, 3600, 'SQL 注入测试'),
              (['hydra', 'medusa'], 120, 7200, '密码爆破'),
              (['hashcat', 'john'], 30, 3600, '密码破解'),
              (['nikto'], 60, 1800, 'Web 漏洞扫描'),
              (['curl', 'wget'], 5, 300, '网络请求'),
              (['ping'], 10, 60, 'Ping'),
              (['traceroute'], 10, 120, '路由追踪'),
              (['dig', 'nslookup', 'host'], 2, 30, 'DNS 查询'),
              (['python', 'python3', 'ruby', 'perl'], 5, 300, '脚本执行'),
              (['apt', 'apt-get', 'yum', 'pip', 'gem', 'npm', 'go install'],
               30, 600, '包安装'),
          ]

          cmd_lower = cmd.lower()
          for keywords, min_s, max_s, reason in KNOWN_DURATIONS:
              for kw in keywords:
                  if kw in cmd_lower:
                      return {'min_seconds': min_s, 'max_seconds': max_s, 'reason': reason}

          # 未被匹配 → 启发式估算
          # 包含网络相关关键词
          if any(kw in cmd_lower for kw in ['http', 'https', '://', 'scan', 'brute', 'enum', 'fuzz']):
              return {'min_seconds': 10, 'max_seconds': 600, 'reason': '网络相关命令'}
          # 长命令（>100 字符）可能比较慢
          if len(cmd) > 100:
              return {'min_seconds': 5, 'max_seconds': 300, 'reason': '长命令'}
          # 无法判断 → 不报警
          return None

五、协同设计的核心价值总结
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  改造前：
    Leader ────阻塞调用────→ ToolMaster ────阻塞调用────→ DataAnalyst
                                                    └───阻塞调用────→ Hawkeye
    问题：
      - ToolMaster 不"知道" DataAnalyst 和 Hawkeye 存在
      - Leader 派发任务后卡住等待，无法并行思考
      - 所有交互是链式串行的，一个卡住全流程停

  改造后（异步消息驱动）：
         ┌─────── POLL ←── CommBus ←── POLL ────────┐
         ↓                                           ↓
      Leader  ←──→  CommBus  ←──→  ToolMaster  ←──→  CommBus
         ↕                ↕                           ↕
       CommBus          CommBus                     CommBus
         ↕                ↕                           ↕
       Hawkeye ──→ 主动告警 ──→ ToolMaster          DataAnalyst
         ↕                                           ↕
       CommBus                                     CommBus
         ↕                                           ↕
       DataAnalyst ──→ 主动告警 ──→ Leader（发现重大漏洞时）

  关键变化：
    1. 同步阻塞 → 异步消息驱动（每个 Agent 独立线程 POLL→PROCESS→THINK→ACT）
    2. ToolMaster 自主决定是否请求 DataAnalyst（而非系统自动触发）
    3. Hawkeye 的告警以自然语言消息到达 ToolMaster 的 Inbox
    4. 所有 Agent 间通信沉淀为结构化消息，可追溯、可复盘
    5. 每个 Agent 的 LLM prompt 明确知道队友的存在和能力
    6. 数据流动从"单向阻塞调用链"变为"多向自主异步协作"
    7. 统一性：所有 4 个 Agent 使用相同的 AgentLoop 引擎，只是 decide() 不同
